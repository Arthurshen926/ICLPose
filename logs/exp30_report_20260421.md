## Regression diagnosis

Historical best oracle result (`0.30 deg / 166 mm`) was not directly comparable to the 2026-04-19 default pipeline runs.

Key differences found:

- historical best used `--num_neighbors 30`
- historical best used `--loftr_mode accumulated`
- docs explicitly mention `render-and-rematch`
- 2026-04-19 default runs used `K=3` and `loftr_mode=individual`
- current learned refinement is not the main source of the large oracle gain

Conclusion:

- the main regression source was evaluation settings and missing rematch, not a total collapse of LoFTR

### 3. Added cumulative rematch toggle for debugging historical behavior

Updated:

- `pose_refine/evaluate_pipeline.py`

Change:

- added `--rematch_cumulative`
- default behavior remains unchanged
- optional mode keeps accepted rematch correspondences across iterations instead of using only `phase-1 + current render`

Why:

- to test whether the historical `render-and-rematch` result came from a different accumulation policy

## Important evaluation nuance

In `pose_refine/evaluate_pipeline.py`, the reported `Refined (S1)` metric can still differ from `LoFTR init` even when `outer_iters=0`.

Reason:

- with `selection=residual`, the code still re-selects among candidate poses using feature residuals

Consequence:

- clean oracle LoFTR reproduction should use:
  - `--selection inlier`
  - `--outer_iters 0`

## Current best reproduced oracle results

Two frontier points now exist:

- best translation median: `0.360 deg / 177.9 mm`
  - `output/pipeline_eval/oracle_k30_accumulated_oi0_inlier_rematch4/results.json`
- best rotation median in this sweep neighborhood: `0.340 deg / 179.2 mm`
  - `output/pipeline_eval/oracle_k30_accumulated_oi0_inlier_rematch4_r6/results.json`

Practical conclusion:

- if the target is best translation median, use `840 + rematch=4`
- if the target is slightly better rotation while staying near the same translation range, use `840 + rematch=4 + reproj_threshold=6.0`

## Final conclusion

- the large oracle gain comes from stronger LoFTR settings plus render-and-rematch, not from the learned refiner
- rematch improves oracle translation from `205.2 mm` to `177.9 mm`
- learned refinement is only a tiny improvement under the strongest clean init
- rematch depth is saturated by `4`
- solver tweaks and cumulative rematch do not recover the historical `166 mm`
- the exact historical `0.30 deg / 166 mm` command is still not reproduced in the current worktree

## Recommended next steps

1. If we want to keep searching for `166 mm`, do only a very small remaining sweep around LoFTR match filtering, e.g. `loftr_conf`.
2. If we want a stable paper/report baseline now, use `oracle_k30_accumulated_oi0_inlier_rematch4` as the reproduced best-translation oracle pipeline and note that the historical number remains unreproduced.
3. Before editing public docs, decide whether to preserve `0.30 deg / 166 mm` as a historical claim or replace it with the currently reproduced number in this worktree.
